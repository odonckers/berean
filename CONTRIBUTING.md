# Contributing to Berean

Thanks for helping build Berean. Bug reports, ideas, design feedback, docs and code are all welcome, and you don't need to be a Rust or React Native expert to help.

By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md). Report security problems privately, as [SECURITY.md](SECURITY.md) describes, not in a public issue.

## Ways to help

- **Report a bug** with the [bug form](https://github.com/odonckers/berean/issues/new?template=bug_report.yml). Steps to reproduce, the device and a screenshot help most.
- **Suggest a feature** with the [feature form](https://github.com/odonckers/berean/issues/new?template=feature_request.yml). Say what you're trying to do in your study, not only the button you'd add.
- **Ask a question** in [Discussions](https://github.com/odonckers/berean/discussions).
- **Pick up an issue.** Issues labelled `good first issue` or `help wanted` are ready to take. Leave a comment first so two people don't build the same thing.
- **Bigger changes** (a new screen, a new FFI surface, a new dependency) start as an issue or a design note in [`docs/design/`](docs/design/README.md), so the direction is agreed before the code.

## Project layout

```
core/            Rust workspace, platform-neutral
                   berean-core     catalog, library, jwpub, search, userdata
                   berean-ffi      UniFFI surface over berean-core
                   uniffi-bindgen  generates the foreign-language bindings
apps/mobile/     Expo (React Native) app for Android and iOS
                   modules/        local Expo modules, incl. berean-ffi-rn (the core's bindings)
apple/           Native SwiftUI apps for iOS, iPadOS and macOS
docs/            Design specs (docs/design) and the feature parity list (docs/parity.md)
```

The Rust core knows nothing about any platform. Every app talks to it through `berean-ffi`.

## Set up

### Rust core

You need Rust 1.95 or newer. `core/rust-toolchain.toml` picks the stable toolchain with rustfmt and clippy.

```sh
cd core
scripts/fetch-fixtures.sh   # downloads the pinned test publications into core/fixtures/
cargo test --workspace
```

The tests read real publication files, pinned by SHA-256 in `core/scripts/fixtures.txt` and downloaded from the publisher's servers. They are gitignored: never commit them.

### Mobile app (Expo)

You need:

- Node 22.13 or newer, and npm
- JDK 17 and the Android SDK, with an emulator or a device
- Rust with the Android targets: `rustup target add aarch64-linux-android x86_64-linux-android`
- `cargo install --locked cargo-ndk@4.1.2`
- Android NDK r30 (`30.0.16248370`), with `ANDROID_NDK_HOME` pointing at it
- For iOS, a Mac with Xcode

```sh
cd apps/mobile
npm ci
npm run ubrn:android   # builds the Rust core and generates its bindings
npx expo run:android   # builds and installs the dev client
npm start              # Metro for the installed dev client
```

The app is a development build (`expo-dev-client`), not Expo Go. `android/` and `ios/` are generated by `expo prebuild` and gitignored, so change `app.json` or a config plugin rather than editing them. Run `npm run ubrn:android` again whenever `core/` changes. [`apps/mobile/README.md`](apps/mobile/README.md) has more on the design system and the dev menu.

### Apple apps

The native Apple apps need a Mac with Xcode 26 and XcodeGen. See the [README](README.md#apple-apps-on-a-mac). Their CI runs on a maintainer's Mac, so it doesn't run for pull requests from forks; a maintainer runs it before merging.

## Before you open a pull request

Run the checks for what you changed. CI runs the same ones.

| Changed | Run |
| --- | --- |
| `core/` | `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` |
| `apps/mobile/` | `npm run typecheck`, `npm run lint`, `npm test` |
| Native code, Expo modules, dependencies | also `npx expo prebuild --platform android` and an Android build |

## Pull requests

- Branch from `main` and keep one change per pull request. Small pull requests get reviewed sooner.
- Fill in the pull request template. Say what a user sees before and after the change.
- **UI changes need screenshots.** Show phone and tablet, light and dark. When the change touches text or layout, also show a large text size. Show the iOS look and the Material look where both apply.
- **Accessibility is part of done.** Labels and roles for screen readers, touch targets of at least 44 pt (48 dp on Android), and layouts that hold up at large text sizes and on tablets and large screens.
- Add or update tests for behaviour changes in `core/`, and for logic in `apps/mobile/src`.
- Don't commit generated code (`berean-ffi-rn` bindings, `android/`, `ios/`, the XCFramework) or publication files.
- A maintainer reviews every pull request. CI must be green before it merges.

### Commit messages

Start the subject with the area, then say what changed in plain words:

```
Core: What's New and Library title search
Expo: bookmark sheet fits its content on tablets
Docs: how to run the fixtures fetch on macOS
CI: cache the NDK between runs
```

Use `Core`, `Expo`, `Apple`, `Docs` or `CI`. Explain the why in the body when it isn't obvious.

## CI, dependencies and releases

- Every pull request runs the `repo` check (versions agree, workflows lint) and, for the parts it touches, the `core` and `mobile` checks. They need no secrets, so they run the same for pull requests from forks. A first-time contributor's run waits for a maintainer to approve it.
- Pull requests are labelled by area automatically. The labels group the release notes, so give your pull request a title that reads well in a changelog.
- Dependabot opens weekly updates for npm, Cargo and GitHub Actions. Expo SDK, React Native and uniffi upgrades are done by hand, together.
- Maintainers cut releases by tagging a version; [docs/releasing.md](docs/releasing.md) has the steps.
